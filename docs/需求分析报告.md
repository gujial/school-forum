# 校园论坛平台需求分析报告

## 1. 项目概述

### 1.1 项目背景
"可圈可点"校园论坛平台是一个专为校园师生设计的社交互动平台，旨在提供一个安全、便捷的校园信息交流环境。平台支持文字、图片、视频等多种内容形式，具备完整的社交功能，包括关注、点赞、评论、私信等。

### 1.2 项目目标
- 为校园师生提供安全可靠的信息交流平台
- 支持多媒体内容发布和分享
- 建立完善的用户管理和内容审核机制
- 提供丰富的社交互动功能
- 实现智能内容审核，保障平台内容质量

### 1.3 技术架构
- **前端**: Vue.js + Nuxt.js + TypeScript
- **后端**: Node.js + H3 + TypeScript
- **数据库**: OceanBase (MySQL兼容)
- **文件存储**: 本地文件系统
- **内容审核**: DeepSeek/Ollama LLM API
- **部署**: Docker + Docker Compose

### 1.4 项目特色
- 智能内容审核系统
- 完整的用户权限管理
- 多媒体内容支持
- 实时社交互动
- 响应式设计，支持多端访问

## 3. 数据流图

![数据流图](./images/数据流图.svg)

### 3.1 主要数据流向

#### 用户操作流程
1. 用户 → 前端界面 → API网关 → 认证中间件
2. 认证中间件 → 用户API → 数据库
3. 数据库 → 用户API → API网关 → 前端界面

#### 内容发布流程
1. 认证通过 → 推文API → 内容审核
2. 内容审核 → LLM服务 → 审核结果
3. 审核通过 → 推文API → 数据库
4. 数据库 → 推文API → 响应结果

#### 媒体上传流程
1. 认证通过 → 媒体API → 文件存储
2. 文件存储 → 媒体API → 数据库记录
3. 数据库 → 媒体API → 响应结果

#### 社交互动流程
1. 认证通过 → 社交API → 数据库更新
2. 数据库 → 社交API → 响应结果

### 3.2 数据存储结构
- **用户数据**: 用户基本信息、认证信息、个人资料
- **内容数据**: 推文内容、评论内容、媒体文件信息
- **关系数据**: 关注关系、点赞记录、标签关联
- **系统数据**: 日志记录、统计数据、配置信息

### 3.3 数据流细化（结合数据库表）
- **用户注册/登录**
  - 输入: 用户名、邮箱、密码哈希
  - 处理: 写入/校验 `Users`，必要时读取 `Avatar` 获取头像
  - 输出: 认证结果、用户资料

- **资料管理（头像/背景）**
  - 输入: 头像文件URL、背景图URL
  - 处理: 更新 `Avatar.avatar_url`、`Users.bg_url`
  - 输出: 更新结果与最新资料

- **发布推文**
  - 输入: 文本内容、可选媒体URL、可选标签集合
  - 处理: 新增 `Tweets`；新增 `Media`（可选）；调用存储过程 `add_tweet_tags` 将逗号分隔标签写入 `TAGS` 和 `TweetTags`
  - 输出: 推文详情、归档后的标签列表

- **按标签检索推文（升/降序）**
  - 输入: 标签集合（逗号分隔）、分页 `limit/offset`
  - 处理: 调用 `get_tweets_by_tags_asc` 或 `get_tweets_by_tags_desc`，联结 `Tweets`、`TweetTags`、`TAGS`
  - 输出: 推文列表（含聚合标签）、时间顺序结果

- **评论与回复**
  - 输入: 推文ID/父评论ID、评论内容
  - 处理: 新增 `Comments`（可带 `parent_id` 支持楼中楼）
  - 输出: 评论详情与时间戳

- **点赞/取消点赞**
  - 输入: 用户ID、推文ID
  - 处理: 写入/删除 `Likes`（受唯一键 `unique_user_tweet` 约束）
  - 输出: 点赞状态与计数

- **关注/取关**
  - 输入: 关注者ID、被关注者ID
  - 处理: 写入/删除 `Follows`；触发器 `before_follow_insert` 防止自关注
  - 输出: 关注状态、粉丝/关注计数

- **私信**
  - 输入: 发送者、接收者、消息内容、可选关联 `tweet_id/comment_id`
  - 处理: 新增 `Messages`
  - 输出: 消息记录与时间戳

- **举报**
  - 输入: 举报对象（推文/评论）、举报人、举报内容
  - 处理: 新增 `Reports`
  - 输出: 举报记录；供管理员处理

- **管理员操作**
  - 输入: 管理员用户ID
  - 处理: 校验是否在 `Admins`；执行删除举报、封禁内容/用户等操作
  - 输出: 管理操作结果

### 3.4 触发器/约束/存储过程对数据流的影响
- **触发器 before_follow_insert**: 在写入 `Follows` 前阻止 `follower_id = following_id`，避免自关注的数据异常。
- **触发器 before_tweet_delete**: 删除 `Tweets` 前级联清理 `Comments`、`Media`、`Likes`、`Messages`、`TweetTags`、`Reports`，确保内容删除后无悬挂数据。
- **触发器 before_comment_delete**: 删除 `Comments` 前清理与之关联的 `Messages`、`Reports`。
- **触发器 before_user_delete**: 删除 `Users` 前清理其 `Avatar`、`Tweets`、`Comments`、`Likes`、`Messages`（作为发送者/接收者）、`Follows`、`Admins`、`Reports` 等，避免孤儿记录。
- **存储过程 add_tweet_tags**: 接收逗号分隔标签，按需在 `TAGS` 去重新增，并在 `TweetTags` 去重插入，实现标签规范化与多对多绑定。
- **存储过程 get_tweets_by_tags_asc/desc**: 基于完整标签集合匹配推文，并返回按时间升/降序的推文及其聚合标签，支持 `limit/offset` 分页；在部分数据库（OceanBase）中使用子查询版本兼容分页行为。
- **唯一/主键约束**: `Users.username/email` 唯一；`Likes(user_id,tweet_id)` 唯一；`TweetTags(tweet_id,tag_id)` 复合主键；`Follows(follower_id,following_id)` 复合主键；其他主键自增保证实体唯一性。

## 5. 系统需求

### 5.1 功能需求
- **用户管理**: 注册、登录、资料管理、权限控制
- **内容管理**: 发布、编辑、删除、审核
- **社交功能**: 关注、点赞、评论、分享
- **搜索功能**: 多维度搜索、智能推荐
- **消息系统**: 私信、通知、提醒
- **管理功能**: 用户管理、内容审核、系统监控

### 5.2 性能需求
- 系统响应时间 < 2秒
- 并发用户数 > 1000
- 数据存储容量 > 100GB
- 系统可用性 > 99.9%

### 5.3 安全需求
- 用户身份认证和授权
- 数据传输加密
- 内容安全审核
- 防SQL注入和XSS攻击
- 用户隐私保护

### 5.4 兼容性需求
- 支持主流浏览器 (Chrome, Firefox, Safari, Edge)
- 响应式设计，支持移动端访问
- 支持多种文件格式 (JPG, PNG, MP4, AVI等)
